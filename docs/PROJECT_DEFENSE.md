# Руководство и материалы для защиты проекта «Fitness Monitoring»
> **Тема**: Проектирование и разработка защищённой отказоустойчивой системы мониторинга показателей здоровья и активности  
> **Стек технологий**: Python 3 (FastAPI, SQLAlchemy 2.0 Async, Alembic, Pydantic v2), PostgreSQL 16, TypeScript (Angular 21, Signals, SCSS), Docker & Docker Compose, GitHub Actions CI.

---

## 1. Введение и архитектура системы

### 1.1 Назначение системы
Программно-аппаратный комплекс «Fitness Monitoring» предназначен для:
1. Непрерывного сбора, агрегации и валидации медицинских телеметрических данных (пульс, шаги, сожжённые калории, сон) с носимых фитнес-устройств.
2. Предоставления пользователям инструментов анализа физической активности, постановки целей и отслеживания прогресса.
3. Предоставления лечащим врачам строго регламентированного и аудируемого доступа к показателям пациентов.
4. Автоматического обнаружения опасных состояний здоровья (хроническая тахикардия, критическая гиподинамия).

### 1.2 Архитектурный стиль
- **Архитектура**: Модульный монолит с четким разделением слоев (Presentation, Service, Data Access Layer) и независимо развертываемым Single Page Application (SPA).
- **Бэкенд**: Асинхронный REST API на базе FastAPI (ASGI Uvicorn).
- **База данных**: Реляционная СУБД PostgreSQL 16 с транзакционной целостностью, пулингом соединений и строгой схемой миграций Alembic (версии `0001`–`0023`).
- **Фронтенд**: Angular 21 на базе автономных компонентов (`standalone: true`), сигналов (`Signals`) и ленивой загрузки модулей (`loadComponent`).
- **Инфраструктура**: Изолированная среда Docker Compose (сеть `internal-net`, непривилегированные пользователи, автоматические проверки работоспособности `healthcheck`).

## 2. Этап 1: Инфраструктура и аудит безопасности (Hardening Tasks 1–7)

### Задача 1. Аутентификация и криптографическое разделение ролей в JWT
- **Было (Уязвимость)**: Система доверяла произвольным HTTP-заголовкам `X-User-Id` и `X-Doctor-Id`. Любой клиент мог подменить заголовок и получить доступ к данным любого пациента или правам врача (IDOR / Spoofing).
- **Сделано**:
  - Полностью исключены небезопасные заголовки `X-User-Id` и `X-Doctor-Id`.
  - Внедрен стандарт RFC 7519 (JSON Web Tokens). Авторизация строго через заголовок `Authorization: Bearer <token>`.
  - Токены содержат обязательные клеймы:
    - `sub` (строковый идентификатор субъекта),
    - `role` (`user` либо `doctor`),
    - `iat` (время выпуска),
    - `exp` (срок действия: 15 минут для Access токена).
  - Строгая валидация подписи (алгоритм `HS256`), проверка срока жизни и защита от атак типа *Algorithm Confusion* (токены с `alg: none` или сторонними алгоритмами отклоняются с кодом `401 Unauthorized`).
  - Внедрены зависимости FastAPI: `get_current_active_user` и `get_current_active_doctor`. Пациент физически не может вызвать методы врача, а врач — методы изменения настроек пациента.

### Задача 2. Управление учетными записями врачей и закрытый Provisioning
- **Было (Уязвимость)**: Отсутствовала аутентификация врачей; любой желающий мог вызвать публичный эндпоинт и зарегистрировать учетную запись доктора.
- **Сделано**:
  - Публичная регистрация врачей полностью заблокирована.
  - Разработан безопасный административный CLI-инструмент: `backend/scripts/create_doctor.py`. Создание доктора возможно только администратором системы через защищенный shell-скрипт с валидацией сложности пароля.
  - Добавлена миграция `0020_add_doctor_auth_columns.py`: в таблицу `Doctors` внесены поля `email`, `password_hash`, `is_active` и уникальное ограничение `uq_doctors_email`.
  - **Двухэтапное хеширование паролей**:
    1. Предварительное хеширование через `SHA-256` (защита от ограничения алгоритма `bcrypt`, который обрезает пароли длиннее 72 байт).
    2. Хеширование с солью через `bcrypt` (защита от словарных атак и радужных таблиц).
  - Эндпоинт `/api/v1/auth/doctor/login` выдает JWT с ролью `doctor`.

### Задача 3. Контроль доступа врача к данным пациентов (Doctor Access Control) & Аудит
- **Сделано**:
  - Доступ врача к медицинской карте пациента разрешается **только при наличии активной записи** в таблице `Doctor_Access`.
  - Временные рамки: `valid_from <= CURRENT_DATE` и `valid_to >= CURRENT_DATE` (строгая включительная логика интервалов дат).
  - При попытке доступа без действующего разрешения API возвращает `403 Forbidden` с понятным сообщением об ошибке.
  - **Неотказуемость и аудит (Audit Trail)**:
    - Любой санкционированный просмотр данных пациента врачом автоматически регистрируется в таблице `Access_Log`.
    - Фиксируются: `doctor_id`, `user_id`, точный `timestamp`, `action` (`view_profile`, `view_readings`, `view_workouts`).
    - Запись аудита выполняется в той же транзакции, что гарантирует достоверность журнала действий.

### Задача 4. Устранение фиктивного механизма PostgreSQL RLS (Row Level Security)
- **Было (Архитектурная проблема)**: В кодовой базе присутствовал файл `rls_shadow.py` и middleware, пытавшиеся эмулировать Row Level Security через установку переменной сессии PostgreSQL `app.current_user_id`. При использовании пулинга соединений (`connection pooling`) установка параметров сессии не является потокобезопасной: одно и то же физическое соединение переиспользуется разными запросами, что приводило к взаимному проникновению данных между клиентами и ложным срабатываниям.
- **Сделано (Вариант B — Application-Level Authorization)**:
  - Фиктивный и нестабильный RLS-shadow полностью демонтирован.
  - Изоляция данных гарантирована на прикладном уровне (Application-Level Security) через ORM-запросы SQLAlchemy с обязательным условием `WHERE user_id = :current_user_id`.
  - Запросы врача строго параметризованы проверкой прав через `Doctor_Access`.
  - Кодовая база очищена от мертвого кода, пустых таблиц логов расхождений и неработающего middleware.

### Задача 5. Принцип наименьших привилегий в PostgreSQL (Least Privilege)
- **Было (Уязвимость)**: Приложение подключалось к БД под пользователем `app_user` с паролем по умолчанию `change_me_please`, имевшим расширенные права.
- **Сделано**:
  - Реализовано четкое ролевое разделение в PostgreSQL:
    1. **Миграционная роль (`superuser` / `postgres`)**: используется только утилитой Alembic при развертывании схемы для выполнения DDL-операций (`CREATE TABLE`, `ALTER TABLE`, `DROP`).
    2. **Роль приложения (`app_user`)**: используется API-бэкендом исключительно в рантайме.
  - Создана миграция `0021_harden_app_user_role.py` и скрипт `backend/scripts/configure_db_roles.py`:
    - Аннулирован дефолтный пароль; учетная запись переведена на безопасную аутентификацию по переменным окружения.
    - Отозваны права `CREATE` на схему `public` у роли `PUBLIC` и у `app_user` (предотвращение атак с внедрением вредоносных функций и DDL-инъекций).
    - Выданы строго минимально необходимые DML-привилегии: `SELECT, INSERT, UPDATE, DELETE` на существующие и будущие таблицы (через `ALTER DEFAULT PRIVILEGES`).
    - Запрещены любые DDL-команды для пользователя приложения.

### Задача 6. Атомарность синхронизации и предотвращение состояний гонки (Sync Concurrency)
- **Было (Проблема надежности)**: При одновременной отправке пакетов телеметрии с нескольких трекеров или при нестабильной сотовой связи возникали дубликаты записей и сбои счетчиков.
- **Сделано**:
  - Эндпоинты `POST /api/v1/sync/reading` (одиночная запись) и `POST /api/v1/sync/batch` (пакетная синхронизация) переведены на строгие атомарные транзакции.
  - При инкременте счетчиков показаний устройства применяется пессимистическая блокировка `SELECT ... FOR UPDATE`, защищающая от гонок при параллельных запросах.
  - Для записей телеметрии внедрен механизм идемпотентности:
    `INSERT INTO Health_Readings ... ON CONFLICT (device_id, recorded_at) DO NOTHING`.
    Повторные пакеты телеметрии не приводят к падению сервиса или дублированию данных.
  - Внедрена строгая дифференциация HTTP-статусов:
    - `409 Conflict`: конкурентные конфликты или нарушения ограничений внешних ключей.
    - `422 Unprocessable Content`: некорректный формат или невалидные физиологические диапазоны.
    - `503 Service Unavailable`: временная недоступность базы данных.

### Задача 7. Контейнеризация, оркестрация и CI/CD
- **Сделано**:
  - Написаны оптимизированные `Dockerfile` для бэкенда (многоэтапная сборка, запуск от непривилегированного пользователя `appuser`) и фронтенда (Nginx reverse-proxy / Angular production).
  - Сформирован `docker-compose.yml`, объединяющий:
    - `postgres`: СУБД с автоматическим healthcheck (`pg_isready`).
    - `db-migrate`: отдельный разовый контейнер миграций Alembic, ожидающий готовности БД.
    - `backend`: API-сервер FastAPI, стартующий только после успешных миграций (`condition: service_completed_successfully`).
    - `frontend`: Angular веб-приложение.
  - Настроен автоматический пайплайн `.github/workflows/ci.yml`:
    - Поднятие сервиса PostgreSQL в GitHub Actions.
    - Накатывание миграций Alembic.
    - Запуск тестов безопасности и функциональности backend (pytest).
    - Сборка и запуск unit-тестов фронтенда (Angular).
  - Оформлен документ `docs/SECURITY.md` с описанием модели безопасности по методике STRIDE.

## 3. Этап 2: Продвинутые механизмы безопасности и жизненный цикл

### 3.1 Вращающиеся Refresh-токены (Rotating Refresh Tokens)
- **Проблема**: При использовании одного лишь короткоживущего токена пользователь вынужден каждые 15 минут заново вводить пароль. Если же сделать Access токен долгоживущим, его перехват злоумышленником скомпрометирует учетную запись надолго.
- **Решение**:
  - Добавлена таблица `Refresh_Tokens` (миграция `0022_stage2_devices_and_refresh_tokens.py`).
  - В базе данных сохраняется криптографический хеш токена (`SHA-256`), дата истечения и признак отзыва `revoked`.
  - Эндпоинт `POST /api/v1/auth/refresh`:
    - Принимает старый Refresh-токен.
    - Проверяет срок годности и статус отзыва в базе данных.
    - **Ротация**: старый Refresh-токен помечается отозванным (`revoked = TRUE`), клиенту генерируется и возвращается совершенно новая пара (Access + Refresh).
  - Эндпоинт `POST /api/v1/auth/logout`: мгновенно отзывает Refresh-токен в базе данных, предотвращая его повторное использование.

### 3.2 Ограничение частоты запросов к авторизации (Rate Limiting)
- **Проблема**: Защита эндпоинтов входа от перебора паролей методом грубой силы (Brute-Force) и распределенных DoS-атак.
- **Решение**:
  - Разработан модуль `backend/app/core/rate_limit.py`.
  - Реализован алгоритм скользящего окна по ключу клиента (IP-адрес + эндпоинт):
    - Лимит: максимум 10 попыток авторизации в минуту.
  - При превышении порога запрос немедленно прерывается с кодом `HTTP 429 Too Many Requests` и информативным заголовком `Retry-After: 60`.
  - Ограничение распространяется на `/auth/login`, `/auth/refresh` и `/auth/doctor/login`.

### 3.3 Пользовательский интерфейс управления доступом врачей (`/settings`)
- **Проблема**: Пациент должен обладать полным суверенитетом над своими медицинскими данными (принцип соответствия GDPR/HIPAA).
- **Решение**:
  - В Angular приложении разработана страница настроек и приватности `SettingsComponent` (`/settings`).
  - Пациент видит интерактивную таблицу всех врачей, имеющих доступ к его данным, с указанием периода действия (`valid_from` — `valid_to`).
  - Реализована функция мгновенного отзыва доступа (`Revoke Access`): отправка запроса `POST /api/v1/doctor/access/revoke` немедленно аннулирует разрешение в базе данных.
  - Разработан сервис Angular `DoctorAccessApiService` для взаимодействия с REST API.

### 3.4 Аппаратные ключи устройств и двойная авторизация (Device Dual-Auth)
- **Проблема**: Синхронизация данных с IoT-трекера не должна зависеть исключительно от пользовательской веб-сессии; устройство должно иметь собственный независимый идентификатор и подтверждение подлинности.
- **Решение**:
  - В модель `Device` добавлены поля `api_key_hash` и `is_active` (миграция `0022`).
  - Каждому физическому трекеру генерируется криптографически стойкий секретный ключ (`dev_...`).
  - При отправке показаний трекер передает заголовок `X-Device-Key`. Бэкенд валидирует соответствие хеша ключа и активность устройства.
  - Если устройство украдено или утеряно, пользователь или администратор может деактивировать его (`is_active = FALSE`) либо выполнить ротацию ключа без удаления истории показаний.

## 4. Фазы 4 и 5: Цели, умные алерты о здоровье, интеграция и QA

### 4.1 Система персональных целей активности (Goals)
- **База данных**:
  - Добавлена таблица `Goals` (миграция `0023_phase4_goals_and_constraints.py`) с внешним ключом на пользователя, полями `goal_type`, `target_value`, `start_date`, `end_date`, `is_active`.
  - Добавлено уникальное ограничение `uq_devices_serial_number` для предотвращения дубликатов серийных номеров устройств.
- **Бэкенд сервис (`GoalsService`)**:
  - Поддержка различных типов целей:
    - `daily_steps` (шаги за день),
    - `weekly_active_minutes` (минуты активности за неделю),
    - `daily_calories` (сожженные калории),
    - `target_heart_rate` (целевая зона пульса).
  - **Динамический расчёт прогресса на лету**: система не хранит статичный процент, а в реальном времени агрегирует фактические телеметрические показатели из `Health_Readings` за текущий расчетный период (сегодня или текущая неделя) и вычисляет точный процент выполнения (`progress_pct`), статус (`in_progress`, `achieved`) и оставшуюся дельту.

### 4.2 Умные медицинские алерты (Smart Health Alerts Engine)
- Сервис автоматически сканирует телеметрию пациента за последние 7 дней на предмет выявления тревожных паттернов:
  1. **Критическая неактивность (Inactivity Alert)**: если за последние 7 дней не зафиксировано шагов или тренировок, формируется предупреждение уровня `WARNING` с рекомендацией начать легкую физическую активность.
  2. **Постоянная тахикардия в покое (High Heart Rate Alert)**: если средний пульс за последние 7 дней превышает 100 ударов в минуту (при наличии достаточного объема показаний), генерируется предупреждение высокого приоритета `DANGER` с настоятельной рекомендацией обратиться к врачу.

### 4.3 Интерфейс целей и здоровья (`/goals`)
- Разработан компонент Angular `GoalsComponent` с маршрутом `/goals`:
  - **Визуальные кольца прогресса (`ProgressRingComponent`)**: интерактивная круговая SVG-диаграмма, плавно заполняющаяся по мере выполнения дневной нормы.
  - **Блок предупреждений о здоровье (Health Alerts)**: карточки с цветовой кодировкой, предупреждающие об отклонениях пульса или длительном простое.
  - **Форма постановки цели**: реактивная форма с валидацией границ значений, позволяющая ставить цели на шаги, калории или время тренировок.

## 6. Шпаргалка для защиты (Ответы на возможные вопросы преподавателя)

### Вопрос 1: «Почему вы отказались от PostgreSQL Row-Level Security (RLS) в пользу авторизации на уровне приложения?»
> **Ответ**:  
> Изначально в проекте была попытка реализовать RLS через установку сессионных переменных PostgreSQL (`SET LOCAL app.current_user_id = ...`).  
> Однако в современных асинхронных бэкендах используется **пулинг постоянных соединений** (Connection Pooling через SQLAlchemy / asyncpg). Сессионные переменные в пуле разделяются между разными HTTP-запросами. Это порождает критическую уязвимость: один запрос может получить соединение с ID предыдущего пользователя, что приведет к утечке персональных медицинских данных.  
> Поэтому мы перешли на проверенную индустриальную архитектуру (**Application-Level Authorization**): идентификатор пользователя извлекается из криптографически подписанного JWT-токена с помощью `Depends(get_current_active_user)` и жестко привязывается к каждому SQL-запросу (`WHERE user_id = :user_id`). Это гарантирует 100% изоляцию и предсказуемость без накладных расходов на переинициализацию соединений БД.

---

### Вопрос 2: «Как устроена защита паролей и токенов от компрометации?»
> **Ответ**:  
> 1. **Пароли**: Мы используем двухэтапное хеширование: `SHA-256` + `bcrypt`. SHA-256 устраняет уязвимость усечения пароля в bcrypt (bcrypt учитывает только первые 72 байта), а bcrypt с солью обеспечивает стойкость к атакам по словарям и аппаратному перебору на GPU. В открытом виде пароли нигде не сохраняются и не логируются.  
> 2. **Access-токены**: Короткоживущие (15 минут), подписаны алгоритмом `HS256`, содержат строгие клеймы ролей.  
> 3. **Refresh-токены**: Хранятся в БД в виде `SHA-256` хеша. Реализован механизм **ротации**: при каждом обновлении старый токен аннулируется, а клиенту выдается новый. Если злоумышленник попытается перехватить старый Refresh-токен, система обнаружит повторную попытку использования отозванного токена.  
> 4. **Rate Limiting**: Эндпоинты входа защищены ограничителем частоты (10 запросов в минуту), блокирующим брутфорс атаки с возвратом HTTP-кода `429 Too Many Requests`.

---

### Вопрос 3: «Что произойдет при одновременной отправке данных с двух трекеров одного пользователя (Race Condition)?»
> **Ответ**:  
> Мы решили эту проблему на двух уровнях:
> 1. **На уровне инкремента счетчиков**: используется пессимистическая блокировка строки устройства `SELECT ... FOR UPDATE`, предотвращающая одновременное изменение состояния устройства.  
> 2. **На уровне сохранения телеметрии**: в таблице `Health_Readings` создан составной уникальный ключ `(device_id, recorded_at)`. Запись выполняется через `INSERT ... ON CONFLICT DO NOTHING`. Если две одинаковые записи придут одновременно, первая будет вставлена, а вторая проигнорирована без сбоя транзакции и без дублирования данных.

---

### Вопрос 4: «Каким образом реализован принцип наименьших привилегий в базе данных?»
> **Ответ**:  
> Мы разделили роли на уровне СУБД:
> - Миграции схемы запускаются под учетной записью суперпользователя (`postgres`) на этапе деплоя.
> - Само FastAPI-приложение в рантайме работает под пользователем `app_user`.
> - У пользователя `app_user` отозваны права `CREATE` на схему `public`, что делает невозможным выполнение DDL-команд (создание, удаление таблиц или триггеров). Ему предоставлены только минимальные права `SELECT, INSERT, UPDATE, DELETE` на прикладные таблицы. Даже при наличии SQL-инъекции атакующий не сможет разрушить структуру базы данных.

---

### Вопрос 5: «Как рассчитывается прогресс выполнения целей и определяются алерты здоровья?»
> **Ответ**:  
> - **Прогресс целей** не хранится как фиксированное число, а вычисляется динамически сервисом `GoalsService`: при запросе система суммирует фактические показатели из `Health_Readings` за расчетный интервал (сегодня или текущая неделя) и сопоставляет их с `target_value` цели, возвращая точный процент и статус (`in_progress` / `achieved`).  
> - **Умные алерты**: анализируют скользящее 7-дневное окно телеметрии. Если за 7 дней нет ни одной записи о шагах, генерируется алерт неактивности. Если средний пульс за 7 дней превышает 100 уд/мин, генерируется предупреждение о тахикардии с рекомендацией консультации врача.
